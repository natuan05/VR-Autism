# Story 3.2: Execute a Timeline node from Unity signals

**Source:** `_bmad-output/planning-artifacts/epics.md`, Story 3.2; Story 3.1 typed Timeline contract. **Date:** 2026-09-29. **Status:** implementation specification.

## Goal and boundary

A schema-2 `Timeline` node starts its configured `PlayableAsset` with a scene-bound Unity `PlayableDirector` and returns `Success` only after the configured Unity Timeline Signal is emitted during that activation. Existing `LessonGraphRunner` activation, cancellation, result commit, edge selection, and telemetry remain the sole graph owner. The Timeline executor owns only one playback and listener session per activation. It returns one `NodeResult` tagged with the input node and activation IDs; it never follows an edge itself.

Story 3.1 already defines `TimelineNodeConfig` (`PlayableAsset`, expected signal name, positive timeout seconds, `Timeout`/`Failed` timeout outcome) and validates authoring. Story 3.2 adds execution support without changing its serialized fields, node enum values, or schema. Story 2.4 supplies only shared ownership boundaries: leave legacy Action/Quest, Quiz/Exploration, LiveKit, Firebase, and scene cutover work in place; parity rows are not acceptance criteria. No scenes, vendors, Python, web, DataPacket or RTDB contracts, checkpoint/resume, Parallel/Gate/Loop runtime, variable/composite edge evaluation, or editor redesign are in scope.

## Runtime contract

1. `LessonGraphValidator.ValidateForExecution` accepts an authoring-valid Timeline node in schema 2 while retaining rejection of Parallel, Gate, Loop, and variable/composite conditions. Schema-1 behavior is unchanged. The runner's `CanStart` still rejects missing executors before activation.
2. A dedicated scene `PlayableDirector` is provided to the production Timeline executor through the existing installer/registry composition. It must not be playing an unrelated asset when a Timeline activation starts. Missing or unusable scene binding fails safely before playback or yields a `Failed` node result; it must never appear as a successful Timeline. Do not create a scene object reference inside `TimelineNodeConfig`.
3. At activation start, identify the expected `SignalAsset` by exact ordinal comparison of its `name` with `ExpectedSignalName` among `SignalEmitter` markers on the configured `TimelineAsset`. Register a transient `SignalReceiver` reaction for each distinct matching `SignalAsset` and bind the Timeline's signal outputs to it before `PlayableDirector.Play`. A `PlayableAsset` that cannot provide the configured Timeline signal must fail without indefinite waiting. Keep and restore preexisting signal-track bindings after playback. Do not alter animation, audio, or other authored track bindings.
4. A signal callback belongs to exactly one playback session. It can produce `Success` once only while that session is current, active, and uncancelled. Unknown assets/names, duplicates, callbacks captured from an earlier activation, and callbacks after cancellation or cleanup are ignored. Playback stopping or reaching its duration is not a success signal.
5. Start a deadline using the existing `INodeClock` and `TimeoutSeconds`. A local deadline or runner `TimeoutToken` returns `NodeStatus.Timeout` or `NodeStatus.Failed` according to `TimeoutOutcome`; a runner skip returns `Skipped`. Lesson abort, pause cancellation, and scene unload cancel the executor, allowing the runner to retain its existing `Aborted`/pause behavior rather than emitting a second completion. If completion and cancellation race, cancellation wins whenever its token is already set before result commitment.
6. On every terminal path (success, configured timeout, external timeout, skip, abort/pause cancellation, scene disable/unload, start failure), synchronously make the session inactive; stop the owned director playback; unregister reactions; restore displaced signal bindings; and release callback/cancellation registrations. Cleanup is idempotent. A scene-lifecycle component performs immediate cleanup on disable/destroy even if an async continuation has not resumed.
7. The dedicated director and its scene bindings are an explicit authoring requirement for a playable scene. Story 3.2 does not edit a scene; manual acceptance must attach/configure it in the worktree Unity project. Other runners/directors must not share that director concurrently.
